# Audio Control R4 — Windows named-pipe client-origin witness

**Windows-only nonproduction test**, not an audio adapter or authority service. It uses standard Windows named pipes plus operating-system APIs to retrieve a connecting process's **actual PID** (`GetNamedPipeClientProcessId`) and security identifier (through `NamedPipeServerStream.RunAsClient` / client impersonation token). It runs on a public GitHub-hosted Windows machine with a real child `dotnet` process and purposely malicious JSON `host_authorized=true`, fabricated PID `987654321` and `S-1-5-18` (SYSTEM) SID. No network listener, audio driver, microphone, speakers, user recordings or credentials.

The caller's JSON data can never substitute for the OS supplied PID/token. This makes a useful donor for a **privileged host-observation adapter** matching an out-of-band authorized process/lease, but it does **not** prove full authorization: named-pipe ACLs, client process trust/signature, same-user processes, PID reuse, session identity, impersonation privileges, service isolation, host restart, token delegation, device permission and actual hardware STOP all remain unqualified. A real host must derive the permitted process/target from a separate OS-trusted mechanism, not the packet and not just a PID.

Build/run on Windows using `dotnet run --configuration Release --project audio-control/platform/windows-pipepeer/PipePeer.csproj`. No NuGet packages beyond .NET 10, no private-runner minutes. This is the Windows complement to Linux `SO_PEERCRED` [#752](https://github.com/SemperSupra/stable-character-pipeline/pull/752) and macOS `getpeereid/LOCAL_PEERPID` [#759](https://github.com/SemperSupra/stable-character-pipeline/pull/759). The product requires the same portable command/receipt contract but OS-specific host identity and device-stop plumbing. Do not merge to production, sign, release, grant controller start or play sound.

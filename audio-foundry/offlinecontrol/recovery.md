# Audio Foundry offline recovery — red-team N3

This workcell probes failures that an in-memory control reducer cannot repair: a validated `scene_audio.v1` WAV may be created while a host crashes before persisting its completion receipt; an existing WAV can be truncated or altered; an orphan file might be mistaken for a completed job.

**Source behavior observed:** the existing offline bridge calls the original Audio Foundry manifest `Plan` and `Render`, and **refuses to overwrite** a pre-existing destination. A verified output SHA-256 can be recomputed, but without a *durable accepted operation record* keyed to principal/session/operation ID, the caller cannot reconstruct an original success receipt or claim exactly-once effect execution. The attached real FFmpeg tests deliberately assert refusal and tamper detection, not successful automatic recovery.

**Required later design, NOT implemented:** host-controlled durable outbox and materialization manifest (idempotency key + full command digest + input source manifest and source bytes hashes + output content hash + checkpoint/epoch + authorized target + provenance). Pre-commit and finalize transitions must be synchronized with the owning filesystem and cleanup policy. Recovery validates exact source plan, output bytes/format/level, host process status and rights before deriving observed success; conflicting/truncated artifacts are quarantined and never overwritten silently. This would need own threat review and actual crash-fault tests, not only synthetic CI.
